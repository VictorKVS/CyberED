# ДЗ F402A-05 — Контроль доступа и аудит в Windows и Astra Linux

**Статус:** подготовлено к выполнению; результаты лабораторных испытаний ещё не получены.  
**Связанный урок:** [Практика Windows и Astra Linux](../site/secure-access-practice.html).  
**Цель:** подтвердить на учебном стенде работу AAA, эффективных разрешений NTFS, Linux RWX/ACL и, при наличии подходящей версии Astra Linux, мандатного контроля целостности.

## Правила безопасности
Только тестовые пользователи и объекты в изолированных виртуальных машинах. Сначала инвентаризация и чтение. Любые изменения учётных записей, политик, аудита и разрешений — только после подтверждения, что стенд выделен для лаборатории. Не менять системные файлы, настройки продуктивных систем, чужие учётные записи и политики организации. Скрывать реальные имена, адреса и идентификаторы в отчёте.

## Часть A. Windows (40 баллов)
1. **Инвентаризация (5):** версия/редакция Windows, доступность MMC, `lusrmgr.msc`, `secpol.msc`, `gpedit.msc`; указать, что недоступно и почему.
2. **AAA и группы (10):** на учебной ВМ создать `LabUser1` и `LabAuditor` после разрешения на изменение стенда; определить группы и права; описать связь членства и фактического доступа. Не использовать реальные пароли в отчёте.
3. **NTFS (15):** создать `C:\CyberED-Lab\Docs\` с тестовым файлом; задать `LabUser1` чтение и проверить отказ в записи, затем исследовать наследование и эффективный доступ. Запреты Deny не добавлять без необходимости. Сохранить матрицу «ожидалось/получилось/почему».
4. **Аудит (10):** изучить события `4624` и `4625`, тип входа и источник, если доступен. Если события не возникают или доступ к журналу запрещён — документировать ограничение, не менять аудит на рабочей машине.

Команды чтения:
```powershell
Get-ComputerInfo | Select-Object WindowsProductName, WindowsVersion, OsBuildNumber
whoami /groups
Get-WinEvent -FilterHashtable @{LogName='Security';Id=4624,4625} -MaxEvents 10 |
  Select-Object TimeCreated,Id,ProviderName
```

## Часть B. Linux / Astra Linux (35 баллов)
1. **Инвентаризация (5):** `cat /etc/os-release`, `uname -r`, `id`; версия и редакция Astra Linux, если установлена.
2. **RWX (10):** тестовый каталог `~/CyberED-Lab/Docs`, тестовый файл; исследовать `r/w/x` для владельца, группы, остальных. Не использовать `chmod -R 777`.
3. **ACL и путь (10):** `stat`, `getfacl`, `namei -l`; объяснить влияние бита `x` на родительских каталогах.
4. **МКЦ (10):** только если механизм поддерживается в установленной версии и разрешён на стенде: записать доступные уровни/метки и выполнить согласованный тест отказа изменения тестового файла. Иначе указать «не проверено: отсутствует поддерживаемый стенд», не имитировать результат.

Команды чтения:
```bash
cat /etc/os-release
uname -r
id
stat -c '%A %a %U %G %n' "$HOME/CyberED-Lab/Docs"
getfacl "$HOME/CyberED-Lab/Docs"
namei -l "$HOME/CyberED-Lab/Docs"
```

## Часть C. Анализ и доказательства (25 баллов)
- **Матрица доступа (10):** субъект, объект, операция, ожидаемый результат, фактический результат, объяснение.
- **Журнал испытаний (10):** дата, ОС/версия, выполненное действие, наблюдение, ссылка на обезличенный скриншот/лог.
- **Выводы (5):** отличия AAA, NTFS ACL, POSIX ACL, МКЦ; минимум три возможные ошибки конфигурации и меры контроля.

## Приёмка
- **90–100:** все применимые проверки воспроизводимы, ограничения честно отмечены, доказательства обезличены.
- **70–89:** основная практика выполнена, имеются небольшие пробелы в анализе.
- **50–69:** частичные проверки без достаточной трассировки.
- **0–49:** результаты не подтверждены или отсутствует существенная часть работы.

**Важно:** отсутствие Astra Linux не считается доказательством работы МКЦ. Для полного балла по этому разделу потребуется подходящий стенд; до его появления раздел помечается как ожидающий выполнения.
