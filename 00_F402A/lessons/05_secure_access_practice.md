## Компетенции FATHER
- **Алина ИБ:** формирует матрицу субъект–объект–операция и доказательную базу проверок.
- **Тима:** инвентаризирует локальные механизмы ОС, фиксирует настройки и их версии, не меняя их без разрешения.
- **Агент аудита:** интерпретирует события 4624/4625, различает факт входа, тип входа и источник.
- **Агент контроля доступа:** проверяет эффективные права NTFS и Linux с учётом групп, наследования, ACL и специальных механизмов.

## 1. Windows: оснастки MMC
Открыть `mmc` через Win+R, добавить «Локальные пользователи и группы» (если доступно в редакции Windows), «Просмотр событий». Для локальных пользователей доступна также `lusrmgr.msc` в поддерживаемых редакциях. Для локальной политики безопасности — `secpol.msc`; для локальной групповой политики — `gpedit.msc` (доступность зависит от редакции). Доменная политика управляется отдельно. Наличие членства в группе не гарантирует фактический доступ: учитываются локальные права, политики запрета, UAC, разрешения ресурса.

### Контрольные точки
1. Снять перечень тестовых пользователей и групп без выгрузки паролей.
2. Зафиксировать парольную политику и блокировку входа, **не меняя** параметры действующей системы.
3. Разобрать жизненный цикл учётной записи: создание → назначение прав → пересмотр → блокировка/отзыв. Отключение вместо удаления может сохранить запись, но не является само по себе гарантией сохранности журналов.

## 2. Windows: события аудита
- **4624** — успешный вход; изучать тип входа, Logon ID и поля источника.
- **4625** — неуспешный вход; изучать Status/SubStatus, тип входа, адрес/имя источника, если заполнены.
События появляются при соответствующей настройке аудита; наличие обоих кодов не означает логирование *всех* этапов AAA. В реальных журналах персональные сведения и имена учётных записей защищать.

Безопасная лаборатория (только чтение):
```powershell
Get-WinEvent -FilterHashtable @{LogName='Security'; Id=4624,4625} -MaxEvents 10 |
  Select-Object TimeCreated, Id, ProviderName, Message
```
Выполнение может потребовать соответствующих прав. Не пересылать необезличенные журналы.

## 3. NTFS: дискреционный доступ
Проверять владельца, наследование, ACE Allow/Deny, группы и эффективный доступ. Упрощённое правило «Deny всегда сильнее Allow» недостаточно: порядок ACE, явные и унаследованные записи, привилегии и путь доступа влияют на результат. Не выдавать избыточный запрет «Полный доступ» для демонстрации запрета чтения: задавать минимально необходимое ограничение на тестовом ресурсе. Администратор не всегда автоматически имеет обычный доступ к содержимому без изменения прав/использования привилегий.

## 4. Astra Linux: модель доступа
В материалах рассматриваются дискреционные права RWX, группы и ACL, а также мандатный контроль целостности (МКЦ). Конкретные доступные уровни, редакции, имена групп и интерфейс зависят от **версии и комплектации Astra Linux**; утверждения о «0 и 63», «AstraAdmin вместо root», «Орёл/Воронеж/Смоленск» не использовать как универсальную спецификацию без документации к установленной версии. Пользовательские уровни конфиденциальности и целостности — не одно и то же.

Команды только для чтения:
```bash
id
stat -c '%A %a %U %G %n' ./Docs
getfacl ./Docs
namei -l ./Docs
```
Команды `getfacl` и `namei` выполняются при наличии утилит. Для доступа к файлу нужны разрешения не только на файл, но и проход (`x`) по каталогам пути. Не менять `/etc/hostname`, системные метки или параметры МКЦ на рабочем компьютере.

## 5. Лабораторная работа: матрица прав
Использовать только изолированный стенд и тестовые учётные записи. Объект `Docs/привет`, субъекты: `User1`, `Auditor`, `Admin`. Заполнить матрицу операций read/write/execute/owner-change, указать ожидаемый и фактический результат, журнал/скриншот, причину расхождения.

**Приёмка:** снимок версии ОС; матрица; события Windows с удалёнными персональными полями; результат эффективных прав; отчёт об ошибках и доказательствах. Для изменения прав или включения аудита необходимо отдельное разрешение.
